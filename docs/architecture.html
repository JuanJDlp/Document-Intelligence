DocuProcess Cloud: architecture

How the platform is deployed on the AWS Academy sandbox (us-east-1): where each component runs, how a document travels from the browser to a result, and which sandbox limits shaped the design. Everything below is derived from infra/terraform/ and specs/.

1. Deployment topology

One VPC across two Availability Zones. Browsers only ever talk to CloudFront. The ALB lives in the public subnets; EC2 instances and RDS have no public IP. S3 and DynamoDB are reached through free gateway endpoints; SNS and SSM go out through the single NAT gateway.

2. Upload and processing flow

The API never processes documents. It stores the file, records a PENDING job and returns 202 Accepted at once. Any worker in the group can claim the job; the browser polls until the status is terminal.

3. Job lifecycle

The jobs table is the queue (ADR-010): there is no SQS. Every transition is a conditional write that checks the expected status and, while RUNNING, the lease owner.

4. Inside an instance

The launch template boots Ubuntu 24.04 LTS (ADR-038) with the pre-existing SSM instance profile. User data installs the application from a versioned release in S3, so a replaced instance comes back identical.

EC2 instance · private app subnet · no public IP · no SSH (SSM Session Manager only)

docuprocess-api.service

Uvicorn, 2 processes, port 8000. Target of the ALB; health check GET /api/v1/health.

Auth and sessions in RDS · uploads to S3 · documents and jobs in DynamoDB.

docuprocess-worker.service

Polls DynamoDB, claims jobs with a lease, persists results, publishes to SNS.

receipt_engine (imported library, no AWS imports) → Tesseract OCR, Spanish and English language packs (ADR-012)

/etc/docuprocess/app.env

Bucket, table and topic names come from Terraform outputs; the DB password is read from SSM at boot and never rendered into user data (SEC-SEC-02).

6. Data placement

Each store holds the data whose access pattern it fits best. The full reasoning is in data-justification.md.

RDS MySQL

  • users: email, Argon2id hash, role
  • sessions: SHA-256 of the token, expiry
  • schema_migrations

Relational, unique email, joins between users and sessions, transactions on login. Small and stable volume.

DynamoDB

  • documents: metadata + result; GSI gsi_user_created for history
  • jobs: status, lease, attempts; GSI gsi_status_available is the queue

Key-value access, conditional writes for claiming, flexible result shape, on-demand capacity with no servers to size.

S3

  • uploads: original PDF / PNG / JPEG
  • artifacts: release tarballs for user data
  • frontend: static site, private behind OAC
  • audit-logs: CloudTrail target

Binary objects up to 5 MiB. Created by a CloudFormation stack that Terraform manages (ADR-035).

8. Verification status

This page describes the design as coded. What has actually been proven so far:

verified locally

  • End-to-end flow with real Tesseract, SQLite and in-process AWS mocks (make demo)
  • Unit, contract and golden tests (make test)
  • Terraform configuration is valid (make tf-validate)

not yet verified in AWS

  • Healthy ALB targets and scale-out to 4 instances
  • Migrations and TLS against RDS
  • Effective instance-role permissions through resource policies
  • SNS email delivery and alarm actions
